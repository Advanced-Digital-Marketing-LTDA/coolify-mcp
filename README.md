# Coolify MCP foundation

A hosted ChatGPT MCP integration that scopes one Coolify team to one pinned server. It implements MCP OAuth endpoints and an OpenID Connect login bridge. It uses synthetic fixtures locally and remains inactive until the owner configures the final HTTPS origin, OIDC client, stable owner subject, and Coolify team token.

## Security model

The outbound client uses Coolify's documented Streamable HTTP MCP endpoint at the deployment-configured HTTPS origin plus the fixed `/mcp` path. Origin and server settings are read once from trusted process configuration; callers cannot choose a host, URL, path, or proxy. Origins with credentials, paths, queries, fragments, non-HTTPS schemes, or nonstandard ports are rejected. Redirects are blocked. At runtime, the adapter validates the published tool schemas and uses Coolify's `server_uuid` and `environment_uuid` filters for resource membership; incompatible schemas or response envelopes fail closed.

Every operation authenticates a verified owner subject and checks the pinned server UUID and configured name against the current Coolify server list. Resource details are returned only after membership is confirmed through the current server-filtered resource list. Projects and environments can span servers; project views include only environments with current resources returned by target-server-filtered lists. Application deploy/restart is denied if `get_server_resources` reports the app on another server or if any server's membership cannot be checked.

Coolify exposes membership checks and writes separately, without an atomic conditional write. The integration rechecks server identity, resource membership, and all visible application destinations immediately before deploy, restart, or configuration writes. A move in the narrow interval between the final check and Coolify's write can still race; no atomicity is claimed.

The published tools provide filtered inventory, safe resource status/details, deployment metadata without logs, and environment key names without values. Normal application deploy and resource restart require exact interactive confirmation. Application configuration updates allow only `name`, `description`, `git_branch`, `base_directory`, `publish_directory`, `ports_exposes`, `watch_paths`, `health_check_enabled`, and `health_check_path`. Health-check paths accept only literal absolute paths using ASCII letters, digits, `/`, `.`, `_`, `~`, and `-`; traversal, query strings, percent escapes, whitespace, quotes, and shell metacharacters are rejected for both stored and proposed values. One field is changed per operation; secrets, source URLs, commands, environment variables, domains, labels, and arbitrary payloads are excluded. The tool displays the exact current-to-proposed diff, requires exact elicitation confirmation, rechecks pinned server and single-server membership, and refuses if the current field changed. The final detail read validates UUID and server evidence. The initiating token and cancellation signal are rechecked immediately before every upstream write. The PATCH request has a 30-second deadline combined with the initiating MCP cancellation signal; cancellation after dispatch cannot undo an upstream change. The write uses only Coolify's fixed `PATCH /api/v1/applications/{uuid}` REST route and a one-field JSON body.

Coolify's current `GetApplication` clears loaded relations before serializing the application. `health_check_enabled` is a top-level application field; `is_auto_deploy_enabled` and `is_force_https_enabled` belong to `ApplicationSetting` and are excluded from this tool because MCP does not reliably supply their current values. Missing, null, or incorrectly typed current fields fail closed; no guessed defaults or Boolean coercion are used.

Diagnostics use a 100-entry in-memory ring buffer. A diagnostic event is fixed to an opaque ID, timestamp, operation enum, outcome enum, and bounded duration. It does not accept or serialize request arguments, resource identifiers, upstream responses, error text, tokens, or payloads. At most 50 entries are returned to the authenticated owner.

Excluded capabilities include secret read/write, shared/global settings, deletion, stop/cancel, force builds, tag/bulk operations, clone, migration, creation, previews, arbitrary upstream calls, and shell execution.

The host uses the MCP SDK OAuth router and `openid-client` for provider discovery, OAuth code exchange, PKCE S256, ID token validation including JWKS signature verification, nonce/state checks, and issuer/audience validation. It accepts a fixed OIDC issuer/client, pins one non-email `sub`, and denies login for any other subject. The SDK serves RFC 9728 protected-resource metadata and OAuth authorization-server metadata, and access tokens are bound to the exact `https://<public-origin>/mcp` resource. DCR is restricted to a single ChatGPT callback URI on the exact `https://chatgpt.com` origin. Public client metadata uses authenticated, process-local HMAC envelopes valid for 30 days, so unauthenticated registrations allocate no client-store entries. SDK endpoint rate limits remain enabled. Refresh tokens rotate; replay revokes the associated grant's access and refresh tokens. Token responses do not expose upstream issuer information. No undocumented Sites identity header is used. Client bearer tokens are verified locally and never forwarded to Coolify; only the deployment-configured Coolify team token is sent upstream.

The host retains one SDK server/transport per authenticated session, preserving initialization capabilities and pending elicitation responses. Sessions are bound to the owner subject and OAuth client ID, limited to 100, and expire after 15 minutes idle or one hour absolute. Authenticated routes and public-origin health requests require the configured public Host and, when present, either the public origin or `https://chatgpt.com` as Origin. A fixed `/healthz` response is also available to direct loopback probes using a literal local Host on the listener port and no Origin; forwarded addresses cannot grant this exception. Forwarded headers do not override these checks; the TLS proxy must preserve the public Host. Set `MCP_TRUSTED_PROXY_CIDRS` to its explicit IP addresses or CIDRs (at most 32). Only these proxies may supply forwarded client addresses for OAuth rate limits; numeric hop counts and wildcard prefixes are rejected. The ingress must overwrite untrusted forwarding headers. Session IDs confer no authorization without a current bearer token. Termination cancels pending work; a write already dispatched upstream cannot be undone.

OAuth signing keys, authorization-code, refresh-token/replay, access-token, and MCP session state are bounded and process-local. Access tokens last one hour; refresh tokens last up to 30 days, subject to the client's 30-day registration lifetime. Access tokens, refresh tokens, and replay tombstones are each bounded to 2,000 entries. Replay tombstones remain until the refresh grant expires; unusually frequent rotation can exhaust capacity and require reconnecting after expiry or restart. Run one application replica; restart invalidates sessions and requires reconnecting. Multi-replica or restart-persistent hosting needs a shared, encrypted OAuth/session store and key management before that topology is enabled.

## Local development

Requirements: Node 22 or newer.

```sh
npm ci
npm run build
npm test
npm run mutation
```

After the activation gates below are satisfied, `npm start` runs the hosted HTTP server from `dist/src/host.js`.

All fixtures are synthetic. Tests cover SDK in-memory protocol plus real loopback HTTP sockets for discovery, OAuth endpoints, and stateful MCP elicitation. A synthetic signed OIDC issuer exercises the real `openid-client` discovery, claim, signature, and token validation. Test transport mapping permits only fixture destinations; no live infrastructure is accessed. HTTP tests cover PKCE, replay, expiry, revocation, cross-client binding, session isolation/limits, Host/Origin rejection, exact approvals, target drift, and write cancellation. CI runs the build, tests, and focused StrykerJS mutation testing over owner identity, configuration, allow-list, scope, confirmation, and error-redaction code. Hosted transport/authentication and upstream adapters have functional coverage but remain excluded from mutation runs to preserve the bounded scope.

The normal test command runs the full suite. Mutation test commands cap Vitest at two workers and stop at the first failed assertion: that already detects the mutant and avoids spending multiple approval-test deadlines on the same injected fault. Mutation scope and score thresholds remain unchanged.

## Docker packaging and synthetic smoke checks

Build the runtime image without activation settings or secrets:

```sh
docker build --tag coolify-mcp:local .
npm run smoke
npm run smoke:docker
```

The Dockerfile pins Node 22 Bookworm slim by digest and installs locked dependencies with `npm ci`. Its final stage contains compiled application code, production dependencies and the loopback health probe, runs as the unprivileged `node` user, and invokes Node directly so SIGTERM reaches the hosted server. Build scripts from dependencies are disabled. Update the base-image digest deliberately when applying Node/Debian security updates. The build context uses an allowlist; `.env` files, Git history, tests, local artifacts and credentials are excluded. There are no build arguments for secrets.

`npm run smoke` builds and runs the production entrypoint with an explicit test preload. `npm run smoke:docker` builds the actual image, starts it with no external network or published ports, mounts only synthetic test fixtures, waits for Docker's healthcheck, and checks the runtime as its non-root user on a read-only filesystem. Both exercise `/healthz`, OAuth discovery, Host/Origin rejection, missing/invalid bearer denial, real signed synthetic OIDC tokens and owner rejection, MCP initialization/tool listing/scoped inventory, session termination and SIGTERM shutdown. The Docker runner also verifies that source, credentials and development dependencies are absent and that an unconfigured image exits with a fixed redacted startup error. The issuer fetch and Coolify provider are fixtures; these checks do not prove live provider or upstream compatibility. Fixtures are never copied into the runtime image. Local smoke uses loopback port 3000; it must be free. Docker smoke uses its private container network namespace.

After the owner completes and approves the activation gates below, `docker compose up --build --detach` starts the example `compose.yaml` using **runtime-only** environment injection from the deployment secret manager. Do not save live secrets to `.env`, Compose overrides, shell history, CI logs or source. `docker compose config` may print interpolated secrets: do not run or share its output with live configuration. Environment secrets remain visible to authorized Docker administrators; protect access to the daemon. The example deliberately fails when required settings are missing. For a direct Docker run, pass variable names (for example `--env OIDC_CLIENT_SECRET --env COOLIFY_API_TOKEN`) from a securely populated process environment; never put secret values in the command or build arguments.

The Compose example drops all Linux capabilities, denies privilege escalation, limits memory/CPU/processes, uses a read-only root filesystem and a small ephemeral `/tmp`, and publishes HTTP on loopback only. A separately configured TLS ingress must preserve the final public Host, overwrite untrusted forwarding headers and match the explicit trusted proxy CIDRs. If that ingress runs in another container, connect it through an appropriately restricted Docker network; its requests are not loopback probes. This example configures no TLS, DNS or live ingress. The healthcheck calls only direct loopback `/healthz` without Origin, forwarded headers or credentials; success means the initialized process is serving, not an ongoing upstream availability check.

Keep exactly **one replica**; do not scale this Compose service or use overlapping rolling replicas. OAuth/session/signing state is process-local, and restart or replacement requires reconnecting. Existing 2,000-entry access-token, refresh-token and replay-tombstone bounds remain unchanged. Deployment, final HTTPS origins, OIDC provider/client selection, owner identity and secure secrets are separate owner steps; container packaging does not activate the integration.

## Activation gates

1. Choose an OIDC provider and register its confidential client with callback `https://<final-mcp-origin>/oauth/callback`. Set `OIDC_ISSUER`, `OIDC_CLIENT_ID`, and `OIDC_CLIENT_SECRET` in trusted deployment settings. The issuer must advertise PKCE S256. Store the client secret only in the host's secret manager.
2. Set `MCP_PUBLIC_ORIGIN` to the final trusted HTTPS origin, without path, query, fragment, credentials, or nonstandard port. This value must match the origin ChatGPT connects to. The previous HTTP dashboard address is not accepted for token-bearing traffic.
3. Pin the owner's stable non-email subject in `COOLIFY_OWNER_SUBJECT`. First-login enrollment is not supported.
4. The approved Coolify target is server **AI Agents**, UUID **pcrionkfci16zmkssngc6vaa**. Set both `COOLIFY_TARGET_SERVER_NAME` and `COOLIFY_TARGET_SERVER_UUID`; both are checked against current Coolify state on each tool call.
5. Set `COOLIFY_ORIGIN` to the confirmed HTTPS Coolify origin and provide the team-scoped token through the host secret manager. The token needs `read`, `deploy`, and `write` abilities for the enabled tools. Do not grant `read:sensitive` or `root`. Never put a live token in source control, `.env`, a prompt, or logs.
6. Configure `MCP_TRUSTED_PROXY_CIDRS` with the actual TLS ingress addresses and configure that ingress to preserve Host and overwrite forwarding headers. Confirm the host's connector approval and network access settings. Run one replica, and verify an owner session, a non-owner session, target resources, and off-target resources before activation. Confirm the deployed Coolify release is patched for [GHSA-4fhp-xqqp-w7vv](https://github.com/coollabsio/coolify/security/advisories/GHSA-4fhp-xqqp-w7vv) (v4.0.0-beta.469 or later) before activation; local path validation does not establish upstream patch status or sanitize other preexisting application settings. No live test or activation is part of this repository change.

This change creates no live connection and does not configure credentials or deploy the service. Remaining owner setup: choose the OIDC issuer/client, securely configure its client secret and stable owner subject, confirm the final HTTPS MCP and Coolify origins, enter a team token with `write`, configure the already-approved AI Agents server pin, and approve the ChatGPT connector in the hosting workspace. Do not use the cleartext dashboard address for bearer-token traffic.
